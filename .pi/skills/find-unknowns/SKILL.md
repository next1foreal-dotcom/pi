# find-unknowns — 帮 Fei 找到他的未知

地图(prompt/上下文)≠ 疆域(代码库/现实约束),差距就是 unknowns。任务越大 unknowns 越多,
产出质量的瓶颈是澄清它们。**你有别的 harness 没有的优势:her-memory 里存着 Fei 知道什么、
做过什么决定、踩过什么坑——每个动作都先用记忆校准,别问 Fei 已经回答过的问题。**

按 Fei 所处阶段挑**一个**动作执行,不全套跑:
陌生领域 → 盲区扫描;看到才知道要什么 → 出方向/mock;大体清楚但有歧义 → 访谈;
有参考物 → 参考移植;活干完了 → 测验。

## 实现前

### 盲区扫描(blindspot pass)
先搜:代码库、git 历史、her-memory(semantic/episodic 里的相关决定与教训)、必要时搜网。
输出四类发现,每条带证据位置:
- **地雷**:会静默失败的危险假设
- **不成文约定**:代码里看不出来的流程步骤
- **缺失概念**:Fei 没意识到存在的关键区分
- **失败先例**:被 revert 的尝试、遗留的老问题(git log + episodic 都要查)

**必须以「改进版 prompt」收尾**:把 Fei 的原始请求蒸馏成带具体约束和推荐顺序的 prompt,
交给 `fable-prompt` 的配方成型。

### 出方向 / 先 mock 再接线
Fei"看到才知道要什么"(视觉/UX/文案)时:做 3-4 个**风格迥异**的方向(HTML 单文件、假数据、
不接后端)让他反应,不要问他要形容词。选定方向后再谈实现。
(记忆里有 Fei 的审美记录——低饱和大地色、编辑式留白等——用它约束方向池,但仍要留一个出格的。)

### 访谈(interview)
需求大体成形但有歧义时:
- **一次只问一个问题**
- **按爆炸半径排序**:答案会改变架构的最先问
- 先列问题清单(标注每题影响什么)再逐题问;her-memory 里已有答案的直接填掉,只问真空白
- 问完把答案回填成更新后的规格/prompt;有长期价值的答案 capture 进记忆

### 参考移植(reference port)
Fei 给了参考物(库/网站/另一种语言的实现)时:读参考物**源码**,提炼语义与行为约定
(不是照抄代码),向 Fei 确认理解后再在目标栈重实现。

### 可调整的计划
出实现计划时**按"Fei 最可能想改的程度"排序,不按执行顺序**:数据模型、类型接口、
用户可见的东西放最前;机械性重构压到底部并注明"这部分不需要你审"。

## 实现中

### 实现笔记
长实现任务开始时建 `implementation-notes.md`:遇到迫使偏离计划的边缘情况 → 选保守方案 →
记入 "Deviations"(是什么/为什么/选了什么)→ 继续干。收尾把 Deviations 汇总给 Fei,
有普适教训的沉淀进记忆——这是下一轮 prompt 的原料。

## 实现后

### 合并前测验(quiz)
长 session 结束、Fei 要 merge/验收前:产出 HTML 报告——新旧心智模型对比、非显然决策点及理由、
依赖的既有假设——底部 5-6 题测验,**答错的题标注对应回哪一节**。防"扫了眼 diff 就合并"。

### 拉认同文档(pitch doc)
需要给别人看时:demo 在最前,spec + 实现笔记打包,预先回答评审者会提的异议(尤其 Deviations 的取舍)。

## 原则

- 每个动作都是"在修复变贵之前廉价地发现无知",挑性价比最高的一个,别仪式化。
- 动作开始前先确认 Fei 的起点:他在思考的哪一步、对问题多熟——先查记忆,再问差额。
- 产出优先用 HTML 工件承载(对比、可点击 mock、测验都远胜纯文字)。
